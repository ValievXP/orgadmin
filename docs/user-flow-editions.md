# User Flow: что входит в MVP, а что в Pro

Документ для разработки. Описывает границу между версиями инструмента и то,
где она задана в коде. Если возникает вопрос «а эта возможность в MVP или в Pro» —
ответ здесь и в одном файле исходников, больше нигде.

---

## 1. Единственный источник правды

Граница объявлена в **`src/lib/user-flow/editions.ts`**, в двух массивах:

```ts
export const PRO_ONLY_STEPS  = ['curator', 'check_result'];
export const PRO_ONLY_EVENTS = ['schedule', 'transfer'];
```

Всё остальное выводится из них автоматически: состав шагов каждой версии, замки
в интерфейсе, проверка сценария, фильтрация буфера обмена, разбор импортируемого файла.

**Чтобы перенести возможность между версиями, правится только этот файл.**
Ни в реестре шагов, ни в панелях, ни в проверке граница больше не описана —
они спрашивают её через `stepAllowed()` и `startEventAllowed()`.

> Раньше в реестре шагов было поле `proOnly`, которое никто не читал. Оно удалено
> намеренно: две записи одного факта рано или поздно разъезжаются.

## 2. Таблица возможностей

| Возможность | MVP | Pro | Что должен уметь бэкенд |
|---|:---:|:---:|---|
| **Шаг «Запуск»** | ✅ | ✅ | Есть всегда, не удаляется, один на сценарий |
| **Шаг «Назначить обучение»** | ✅ | ✅ | Назначение элемента каталога сотруднику со сроком |
| **Шаг «Отправить уведомление»** | ✅ | ✅ | Отправка в push / Telegram / Email / SMS с учётом языка сотрудника |
| **Шаг «Ожидание»** | ✅ | ✅ | Отложенная задача; подписка на факт прохождения с тайм-аутом |
| **Шаг «Развилка»** | ✅ | ✅ | Переход по метке в зависимости от поля профиля |
| **Шаг «Финиш»** | ✅ | ✅ | Закрытие сценария для участника |
| **Шаг «Назначить куратора»** | ❌ | ✅ | Механика кураторства: закрепление сотрудника за куратором |
| **Шаг «Проверить результат»** | ❌ | ✅ | Доступ к результатам обучения: баллы, прогресс, факт прохождения |
| **Запуск «Сотрудник появился»** | ✅ | ✅ | Хук на создание пользователя |
| **Запуск «Вручную»** | ✅ | ✅ | Кнопка и выбор людей |
| **Запуск «По расписанию»** | ❌ | ✅ | Планировщик повторяющихся запусков с защитой от повторной выдачи |
| **Запуск «Сменились должность или отдел»** | ❌ | ✅ | Журнал изменений профиля — сейчас платформа их не хранит |
| Аудитория и правила отбора | ✅ | ✅ | Выборка сотрудников по полям профиля |
| Тихие часы | ✅ | ✅ | Откладывание отправки до начала рабочего окна |
| Правило повторного входа | ✅ | ✅ | Хранение факта прохождения сценария участником |
| Проверка сценария | ✅ | ✅ | Только фронтенд, считается по схеме |
| Мониторинг участников | ✅ | ✅ | Таблица состояний участников — см. п. 5 |

Развилка на несколько веток **намеренно оставлена в MVP**: для бэкенда это тот же
переход по метке, что и обычное условие, а без неё теряется главный сценарий —
«этим одно обучение, тем другое».

## 3. Почему граница проведена именно так

По **стоимости исполнения на бэкенде**, а не по сложности интерфейса.

В MVP попало то, что работает на уже существующих механизмах платформы: создание
пользователя, назначение контента, отправка уведомления, отложенная задача.

В Pro попало то, для чего механизма ещё нет:

- **Планировщик** — повторяющиеся запуски требуют устойчивого расписания,
  идемпотентности и ответа на вопрос «кого не брать во второй раз».
- **Журнал изменений профиля** — чтобы поймать перевод сотрудника, нужно хранить
  историю изменений должности и отдела. Сейчас хранится только текущее значение.
- **Результаты обучения в реальном времени** — баллы и прогресс нужны на момент
  выполнения шага, а не в отчёте.
- **Кураторство** — отдельная сущность с зоной ответственности.

---

## 4. Как граница защищена в коде

Замок в интерфейсе — не единственная защита. Шаг из Pro может попасть в MVP-сценарий
тремя путями, и каждый закрыт:

| Путь | Что происходит |
|---|---|
| Кнопка «Добавить шаг» | Шаг показан с замком и причиной, нажатие заблокировано |
| Вставка из буфера (Ctrl+V) | Буфер общий для версий; Pro-шаги отфильтровываются, показывается «пропущено N» |
| Импорт файла из Pro | Сценарий загружается, но в списке выводится предупреждение с перечнем возможностей |
| Любой из путей | «Проверка сценария» даёт **ошибку**, включение блокируется |

На холсте Pro-шаг всегда помечен бейджем `PRO`. Если он оказался в MVP-сценарии,
карточка становится красной с подписью «Недоступен в этой версии».

Ключевая функция: `unsupportedSteps(edition, steps)` в `editions.ts`.

## 5. Что в прототипе имитировано

Прототип работает на мок-данных. При переносе на платформу заменяется источник
данных, интерфейс не меняется:

| Модуль | Что имитировано | Чем заменить |
|---|---|---|
| `lib/platform/profile.ts` | Список сотрудников и справочники | Запрос к API с фильтром |
| `lib/platform/channels.ts` | Признак подключённости канала | Настройки интеграций организации |
| `lib/user-flow/data.ts` | Дерево контента | Каталог платформы |
| `lib/user-flow/participants.ts` | Состояние участников вычисляется из схемы | Таблица состояний участников |
| `lib/user-flow/storage.ts` | localStorage | API сценариев |

**Важно про мониторинг.** Сейчас `participantsOf(flow, atTime)` вычисляет, где
находится каждый участник, прямо из схемы: развилки разбираются по настоящим данным
профиля, моделируется только скорость прохождения. В проде это должна быть таблица:
участник, сценарий, текущий шаг, время входа, состояние. Форма данных
(`Participant`) уже описана — менять интерфейс не придётся.

---

## 5а. Чего в продукте быть НЕ должно

Прототип читается буквально, поэтому всё, что существует только ради показа,
помечено прямо в интерфейсе компонентом `PrototypeOnly` — сиреневая рамка
с подписью «Заглушка прототипа · в продукт не переносить».

| Что | Где | Почему это заглушка |
|---|---|---|
| Переключатель «Состояние на: Сегодня / +3 дн. / +30 дн.» | Панель «Участники» | Экран не на чем показать: сразу после включения участников нет. В продукте состояние приходит из данных, перемотки времени быть не может |

Если появляется что-то ещё «только для демонстрации» — оборачивать тем же
компонентом. Немаркированный элемент считается частью продукта.

**Отдельно: тексты интерфейса пишутся для пользователя платформы, а не для нас.**
Постановки вида «нужен планировщик повторяющихся запусков» живут в `PRO_REASON`
и в этом документе — в интерфейсе показывается короткое «Доступно в User Flow Pro».
Слова «MVP», «прототип», «мок» в интерфейс не выносятся.

---

## 5б. Каналы уведомлений: временное состояние

`connected` в `lib/platform/channels.ts` — это **состояние интеграций
организации**, а не константа продукта. Сейчас там зафиксировано текущее
положение дел:

| Канал | Состояние | Что делать |
|---|---|---|
| Push | подключён | — |
| Telegram | подключён | — |
| **Email** | **не подключён** | Включить, когда появится отправка писем |
| **SMS** | **не подключён** | Включить, когда появится SMS-шлюз |

Отключённый канал нельзя выбрать в шаге «Отправить уведомление», а если он всё
же выбран в старом сценарии — «Проверка сценария» даёт ошибку и включение
блокируется. Когда каналы появятся, значение должно приходить из настроек
интеграций, а не правиться в коде.

---

## 6. Формат сценария

Схема версионирована: `SCHEMA_VERSION` в `types.ts`. Сценарии, сохранённые старой
версией, переносятся при чтении (`migrateFlow` в `storage.ts`) и сразу
перезаписываются в новом формате.

При несовместимом изменении формата: поднять `SCHEMA_VERSION` и дописать перенос.
Экспорт в файл всегда содержит версию — импорт файла из более новой версии
отклоняется с понятным сообщением.

**Известное ограничение:** у версий разные ключи хранилища
(`osnova-user-flow-mvp` и `osnova-user-flow-pro`). Сценарии между версиями
автоматически не переносятся — только через выгрузку и импорт.

## 7. Что нельзя сломать

Правила, на которых держится корректность. Если менять — то осознанно:

1. **Шаг «Запуск» один и неудаляемый.** Защита стоит в `deleteSteps`, при загрузке
   он добавляется, если отсутствует. Пустого холста быть не может.
2. **Из одного выхода ведёт ровно одна связь.** Сценарий исполняется
   последовательно; вторая связь из того же выхода была бы молча проигнорирована,
   поэтому новая заменяет прежнюю.
3. **Охват и список сотрудников считаются одной функцией** (`audienceOf`). Если
   число на экране и список разойдутся, инструменту перестанут доверять.
4. **Горячие клавиши сравниваются по `event.code`, а не по `event.key`.**
   При русской раскладке `event.key` возвращает «ф», «с», «м», «я» — сочетания
   перестают работать, и срабатывает поведение браузера.
5. **У каждого выхода шага есть `id`.** Связь ссылается на выход по имени; у ручки
   без `id` связь молча не отрисуется, хотя в данных будет.
6. **Сценарий задерживают только шаги ожидания.** Срок прохождения у контента —
   это ограничение для сотрудника, а не пауза: назначение мгновенно, сценарий
   идёт дальше сразу. Если считать дедлайны, оценка срока завышается в разы.
7. **Обратные связи не участвуют в раскладке холста.** Иначе каждый проход по
   циклу опускает шаг ниже, и сценарий растягивается на пустое место.
8. **Сценарий обязан иметь выход.** Если из шага нельзя дойти до «Финиша» или до
   шага без продолжения — участник ходит по кругу вечно. Проверка это ловит и
   блокирует включение (`canFinishFrom` в `check.ts`).
